# next-hono-example

A **server-owned dynz schema**, rendered and validated on both sides.

Hono runs *inside* the Next.js process — one Node instance, no second server, no proxy, no CORS. The page loads the schema over a typed `hono/client` call during the server render, hands it to a client component that renders a form it has never seen before and validates against it, and the server then validates the submission against the very same schema.

```
GET  /api/forms/expense-claim   the dynz schema + server defaults + policy
POST /api/claims                submit; re-validated server-side
GET  /api/openapi.json          OpenAPI 3.1, request body generated by @dynz/to-json-schema
GET  /api/docs                  Swagger UI over that document
```

## Running it

```bash
pnpm install
pnpm --filter next-hono-example dev
# http://localhost:3000        the form
# http://localhost:3000/api/docs   Swagger UI
```

## How the pieces fit

### Hono inside Next

`src/app/api/[[...route]]/route.ts` is a catch-all route handler that hands every `/api/**` request to the Hono app via `hono/vercel`'s `handle()`. Same process as the pages.

```ts
export const runtime = "nodejs";
export const GET = handle(routes);
export const POST = handle(routes);
```

### The schema is the source of truth

`src/server/expense-claim-schema.ts` is the only place the form is described, and it never ships as code — only as data:

| Field | Behaviour |
| --- | --- |
| `employeeId` | frozen (`mutable: false`) — the server owns it |
| `categoryDetails` | exists only for the "other" category |
| `travel` | a whole nested section, only for travel claims |
| `travel.transport` | the "flight" option enables itself for international trips |
| `travel.kilometers` | exists only when travelling by car |
| `travel.plateNumber` | required only for a company car |
| `exchangeRate` | exists only for non-EUR claims |
| `receiptNumber` | required from €50 upwards |
| `approverEmail` | required for large claims **or** hardware (`or`) |
| `clientName` | exists only for billable claims |
| `clientReference` | billable **and** over €100 (`and`) |

Change a threshold in that file and every client follows on its next page load. No frontend deploy.

### Type safety across the wire

Both clients are built from the Hono route type with `hc<AppType>`, so request bodies, response bodies and status-code unions are all checked at compile time.

`src/lib/client.ts` is the browser one, used for the submission:

```ts
const response = await client.api.claims.$post({ json: values });

if (response.status === 201) {
  const body = await response.json(); // { ok: true, id: string, values: … }
}
```

`src/lib/server-client.ts` is the same client with the Hono app's own `request()` handler
swapped in for `fetch`. Because Hono is in this process, a server component calling the API
never makes an HTTP request to itself — no socket, no absolute URL to configure — while the
route handlers still run exactly as they would for a browser:

```ts
export const serverClient = hc<AppType>("http://server", {
  fetch: (input, init) => Promise.resolve(routes.request(…, init)),
});
```

`src/app/page.tsx` uses it to load the form during the server render, so the markup arrives
complete — no loading state and no client-side waterfall:

```tsx
const response = await serverClient.api.forms["expense-claim"].$get();
const { schema, defaults, policy } = await response.json();
```

A dynz schema is plain data, so it crosses the server/client boundary into `ExpenseClaimForm`
as-is. Conditions are resolved during SSR too: the initial HTML contains `employeeId`
(`readOnly`, because `mutable: false`), `category` and `amount`, and genuinely omits
`categoryDetails`, the whole `travel` section, `exchangeRate`, `clientName` and
`clientReference` — none of their conditions hold yet.

The *schema* itself is deliberately handled as runtime data (`ObjectSchema<never>`) — the renderer in `src/components/fields.tsx` walks whatever it is handed and picks a control per `SchemaType`, recursing into nested objects. That is the point: it does not know this form at build time.

### OpenAPI from the schema

`src/server/openapi.ts` runs `toStandardJsonSchema()` over the dynz schema and drops the result straight into `components.schemas`. OpenAPI 3.1 embeds JSON Schema 2020-12, which is exactly what the converter emits, so the documented request body cannot drift from what the server validates.

Conditional properties have no JSON Schema equivalent, so the conversion drops them — which is precisely why the app loads the dynz schema rather than the OpenAPI document. **JSON Schema describes the shape; dynz describes the behaviour.**

### Two validation passes

1. **Browser** — `useDynzForm` from `@dynz/react-hook-form` validates with the dynz resolver. `handleSubmit` only calls through once it passes.
2. **Server** — `POST /api/claims` runs `validate()` against the same schema, with `currentValues` supplying the fields the server owns. A client is not a security boundary.

Failures come back as dynz errors and are mapped onto the matching form fields:

```ts
for (const error of body.errors) {
  methods.setError(error.path.slice(2), { type: error.code, message: error.message });
}
```

Try it from the command line to see the second pass reject what the browser would have blocked:

```bash
curl -s -X POST localhost:3000/api/claims -H 'content-type: application/json' \
  -d '{"employeeId":"EMP-9999","category":"meals","amount":12,"currency":"EUR",
       "description":"Lunch with a candidate","billable":false}'
# → 422  { "ok": false, "errors": [ { "path": "$.employeeId", "code": "immutable", … } ] }
```

## Pinned versions

`react`, `react-dom` and `react-hook-form` are pinned to exact versions here. `@dynz/react-hook-form` resolves its own `react-hook-form` peer in this workspace, and pnpm keys peer-resolved copies by React version — if the app and the integration end up on different copies there are two React contexts at runtime, and `useFormContext()` returns `null`.
